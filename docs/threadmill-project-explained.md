# Threadmill：给第一次接触者的解释

Threadmill 本质上是一个“把用户的软件任务交给一组受边界约束的 Agent 来完成”的运行时系统。它要解决的核心问题是：怎样让多个 Agent 能协作改代码、跑工具和验收结果，同时不互相越权、不把错误的“已完成”传给用户。

## 先记住最简单的主流程

把用户说的“给项目加一个功能”想成一次小型软件项目：

```text
用户
 ↓
Manager
 ↓
Task
 ↓
Planner
 ↓
Executor
 ↓
Verifier
 ↓
Manager
 ↓
用户
```

例如，用户说：“给 CLI 加 `--json` 输出，并补测试。”

- **Manager** 接收请求，建立一个任务。
- **Planner** 先读仓库，找出 CLI 真正的入口、现有输出方式和测试位置，写出可执行计划。
- **Executor** 在工作区实现功能、写测试、运行命令。
- **Verifier** 不相信“我做完了”这句话，而是自己检查代码、跑门禁、做独立试验，给出 PASS / FAIL / INCONCLUSIVE。
- **Manager** 根据验收证据向用户汇报；它不能把“任务流程结束”误说成“功能已经验收通过”。

这里有一个非常重要的区分：

> 一个 Agent 是系统中的一个角色；Threadmill 是把角色、任务图、工作区、记忆、工具隔离与持久化组合起来的整个系统。

没有 Threadmill，四个 Agent 只是四段提示词；有了 Threadmill，它们才在同一套规则下传递工作、文件和证据。

## 1. 角色分工：谁负责什么

### Manager：项目经理，而不是开发者

现实类比：Manager 像项目经理，负责接需求、分配工作、确认验收结果并向客户反馈。

真实系统中，它比项目经理更“受限”：它是唯一能和用户说话、唯一能修改 Coordination Graph（协调图）的角色，但它不能自己读写项目文件、执行命令、实现功能或做最终核验。

| 问题 | Manager 的答案 |
|---|---|
| 它是干什么的？ | 接收用户请求，把需要项目证据的请求变成 Task；维护任务之间的协调关系。 |
| 为什么需要它？ | 否则每个 Agent 都能对用户答复、随意创建任务，系统会失去全局秩序。 |
| 它能做什么？ | 定义 Task Info、创建任务、批准合法的并行帮助任务、读取任务报告、向用户收尾说明。 |
| 它不能做什么？ | 不能直接改代码、跑测试、替 Planner 设计实现，也不能因为 Executor 自称完成就宣布成功。 |

Manager 写的 **Task Info** 是任务合同。它应包含目标、授权范围、硬约束、精确接口或输出、验收标准、已知上下文；它不应抢先猜测实现细节。

```text
目标：CLI 支持 --json
硬约束：现有文本输出不能改变
验收：--json 输出合法 JSON；现有 CLI 测试继续通过
```

这不是“实现方案”，而是后面所有角色都必须遵守的合同。

### Planner：技术方案设计者，而不是调度员

现实类比：Planner 像在开工前调查代码库、画施工图、列验收标准的技术负责人。

真实系统中，Planner 有一个一次性的、可丢弃的工作区。它可以读代码、搜索调用方、看测试、做调查性命令；但它的文件改动不会成为交付物。

| 问题 | Planner 的答案 |
|---|---|
| 它是干什么的？ | 把 Task Info 转成“如何完成、如何拆分、如何验收”的计划。 |
| 为什么需要它？ | Executor 若直接凭需求改代码，容易改到名称相似但行为不对的入口，或遗漏边界条件。 |
| 它能做什么？ | 调查真实行为入口、定义验收矩阵、判断是否可并行、描述依赖与最终集成点。 |
| 它不能做什么？ | 不与用户聊天、不改协调图、不留下最终实现。 |

Planner 和 Manager 最容易混淆：

```text
Manager：这个任务应不应该创建？任务之间怎样安全协调？
Planner：这个任务内部该怎么完成？哪些部分可以拆开？
```

换句话说，Manager 管“项目队列和交通规则”，Planner 管“某个任务的技术施工图”。

### Executor：开发工程师

现实类比：Executor 像真正写代码、补测试、跑构建的开发工程师。

它工作在任务的**持久工作区**中。这里的“持久”不是永久保存一切，而是说：它完成后，正常项目路径中的文件状态会传给后续验收和修复任务。

| 问题 | Executor 的答案 |
|---|---|
| 它是干什么的？ | 按 Task Info 和 Planner 计划完成实际改动。 |
| 为什么需要它？ | 计划本身不能改变软件；必须有一个角色把计划落成代码和可检查的文件状态。 |
| 它能做什么？ | 读取项目规则、编辑文件、写持久测试、运行构建与测试、整合帮助任务结果。 |
| 它不能做什么？ | 不与用户对话、不改协调图、不宣布最终 PASS；不能用删测试或弱化测试来“制造通过”。 |

一个关键点：Executor 的“完成”只表示“我认为交付物已经准备好了”，不是最终事实。

### Verifier：独立 QA / 验收人员

现实类比：Verifier 像独立 QA 或验收人员，而不是同一个开发者给自己打勾。

真实系统中，它同样在一次性的工作区中工作。它可以读取文件、运行命令、做临时 probe（小型独立试验），但不能修代码。

| 问题 | Verifier 的答案 |
|---|---|
| 它是干什么的？ | 独立判断 Task Info 的要求是否真的满足。 |
| 为什么需要它？ | “代码能编译”或“开发者自写测试通过”都可能掩盖错误入口、遗漏边界或错误预期。 |
| 它能做什么？ | 从需求建立验收条件、运行构建/新增验收/全量回归、用公共入口做独立试验，给 PASS、FAIL 或 INCONCLUSIVE。 |
| 它不能做什么？ | 不修复实现、不改计划、不调度后续任务、不向用户直接宣告成功。 |

三种结论的含义：

```text
PASS          已有足够直接证据证明要求成立
FAIL          已观察到要求、交付物或硬约束不成立
INCONCLUSIVE  证据不足，且替代验证路径也无法消除不确定性
```

特别注意：

```text
Task done ≠ Verifier PASS
```

`done` 只是任务流已经走到终态；可能是失败、环境阻塞，或验收证据不完整。架构治理文档明确把这两件事分开。

## 2. Coordination Graph：让多个任务不会乱跑的图

先看一个具体例子。假设需求是：

> 分别实现三个互不相关的 provider，并统一接到注册表和回归测试中。

三个 provider 可以同时做，但“注册表整合”和“全量测试”要等前面都完成：

```text
                 ┌─ Provider A ─┐
Planner ────────┼─ Provider B ─┼──→ Integration ─→ Verifier
                 └─ Provider C ─┘
```

这就是 **Coordination Graph**：记录任务节点及依赖边的任务图。你可以先把它理解成“项目甘特图的可执行版本”。

| 问题 | Coordination Graph 的答案 |
|---|---|
| 它是干什么的？ | 记录哪些任务存在、谁依赖谁、哪些可以启动、结果应汇合到哪里。 |
| 为什么需要它？ | 否则并行 Agent 可能重复工作、并发写同一文件、漏掉收尾集成，或产生循环依赖。 |
| 它能做什么？ | 表达 Root、Spawn、Join、Help，以及 Planner → Executor → Verifier 的固定工作流。 |
| 它不能做什么？ | 不负责实现代码、不替 Agent 判断业务逻辑，也不允许任意增加角色或边类型。 |

图中常见词的白话解释：

- **root task**：由用户请求直接开始的主任务。
- **spawn / helper**：主任务请求的辅助任务。
- **join**：辅助任务结果汇回目标角色。
- **fan-out**：一个节点完成后，分叉启动多个独立工作。
- **fan-in**：多个分支结果汇到一个集成节点。
- **ready frontier**：当前所有“前置依赖已完成、现在就能开工”的节点集合。
- **DAG**：有向无环图；简单说，就是任务依赖不能绕一圈又依赖回自己。

### sequential、parallel、mixed 到底差在哪

#### Sequential：必须排队

例如“先查清现有认证接口，再基于它修改调用方”。

```text
调查真实 API
   ↓
修改调用方
   ↓
测试
```

后一步必须读取前一步的结果，不能为了并行而强拆。系统应保留一个 Executor 的连续推理链。

#### Parallel：彼此独立，同时做

例如“三个 provider 各自位于不同模块、测试和写入范围不重叠”。

```text
        ┌─ Provider A ─┐
开始 ───┼─ Provider B ─┼──→ 汇总
        └─ Provider C ─┘
```

它们可以并发，这叫 fan-out。

#### Mixed：有阶段，但阶段内部可并发

例如先确定统一接口，然后三组实现并行，最后集成。

```text
接口调查
   ↓
 ┌─ A 实现 ─┐
 ├─ B 实现 ─┼→ 注册与集成 → 全量验收
 └─ C 实现 ─┘
```

这就是 mixed：不是“全串行”或“全并行”，而是顺序阶段之间有并发波次。

### 新设计如何做任务拆分

`agent-prompts-after.md` 的核心变化是：**Planner 设计任务内部的拆分，但不直接改图；Executor 按原计划请求帮助；Manager 只做安全校验与实际图修改。**

```text
Planner
  写 Help Executor 计划
       ↓
Executor
  提交当前 ready frontier 的帮助请求
       ↓
Manager
  校验边界、依赖、写入范围、容量
       ↓
并行 helper tasks
       ↓
自动 join 回 Executor
       ↓
Executor 集成与验证
```

这解决了旧设计的一个实际问题：审计发现 78 个可审计题目里产生了 287 个 root task，却没有 spawned helper。结果是反复串行地追加修复根任务，慢，而且一旦连续猜错根因，系统容易陷入“同一种修补重复失败”的僵局。

新设计的改善不只是“多开 Agent”：

- 只让真正独立、有明确交付物和验收方式的部分并行。
- 两个分支若写同一文件区域或同一状态，必须重新划分或显式排序。
- 共享前置只做一次，完成后立即 fan-out。
- 多个分支都完成后必须经过明确的 integration 节点。
- 大任务可递归拆分，但当前层只物化已 ready 的部分，不把几百个后代全塞进 Manager 上下文。

因此，并发不是指标，也不是“把 Agent 数量凑满”；它是由独立交付物和真实依赖决定的。

## 3. VFS 与 Sandbox：文件隔离和命令隔离

先用一个容易出错的场景理解它们：

> Planner 想试验一个修改；Executor 真正修改了代码；Verifier 想运行会生成临时文件的测试。

如果三者直接共用同一目录，Planner 的试验可能污染 Executor 的交付，Verifier 的临时副作用也可能误变成项目改动。

### VFS：给每个角色不同的“文件视图”

**VFS（Virtual File System，虚拟文件系统）**可以先理解为：系统给不同任务和角色准备、快照、合并和回收工作区的机制。

| 问题 | VFS 的答案 |
|---|---|
| 它是干什么的？ | 管理工作区快照、fork、overlay、diff、merge、恢复与清理。 |
| 为什么需要它？ | 要让调查、实现、核验相互隔离，同时让真正需要保留的改动正确传递。 |
| 它能做什么？ | 让角色从同一基线分叉；把 join 结果合并到正确目标；保留无冲突改动并标记冲突。 |
| 它不能做什么？ | 不向 Agent 暴露内部存储；不能逃出配置根目录；不能为了快而牺牲隔离和文件正确性。 |

最重要的工作区区别：

```text
Planner workspace   一次性；用来调查和写计划；结束即丢弃
Executor workspace  持久；实现与提交测试在此留下最终工作树状态
Verifier workspace  一次性；用来独立检查；不能修复持久实现
```

所以，Planner 在自己的空间里改了文件，不代表功能已经实现；Verifier 产生的临时文件，也不应成为交付物。

### Sandbox：给命令一个安全边界

**Sandbox（执行沙箱）**是运行 `go test`、构建命令、脚本等程序时的隔离环境。

| 问题 | Sandbox 的答案 |
|---|---|
| 它是干什么的？ | 隔离命令执行、管理并发、超时、取消、输出限制和进程清理。 |
| 为什么需要它？ | Agent 能运行命令，但不能因此静默跑到宿主机、跨工作区修改文件或留下失控进程。 |
| 它能做什么？ | 按环境分隔可写状态；排队和公平调度；取消超时命令；记录后端与网络模式。 |
| 它不能做什么？ | 没有可用沙箱时不能偷偷在宿主机直接执行；不能复用不同环境的可写状态。 |

VFS 管“看见哪些文件、文件结果如何传递”；Sandbox 管“命令怎样安全地运行”。两者有关，但不是同一个东西。

## 4. Memory Graph：不是文件状态，而是可追溯的任务记忆

想象一个长任务经历三轮：

1. 用户要求公开 API 名必须是 `parseConfig`。
2. 第一轮测试失败，发现错误信息不匹配。
3. 第二轮修复后，构建成功，但全量回归因缺依赖未执行。

文件状态只能告诉你“现在代码长什么样”。它不能可靠表达：

- 原始 API 名不能被缩写或遗忘；
- 哪个结论有测试命令和退出码支持；
- “全量回归通过”是事实、猜测，还是已经被新证据推翻；
- 下一轮修复还必须保留哪些历史约束。

这就是 **Memory Graph（记忆图）** 的用途：它是由节点与关系组成的长期任务记忆，不是代码仓库的副本。

| 问题 | Memory Graph 的答案 |
|---|---|
| 它是干什么的？ | 保存任务目标、逐字契约、证据、假设、失败、决定与状态。 |
| 为什么需要它？ | 长上下文会溢出，多轮修复会遗忘原需求，且错误结论会污染后续任务。 |
| 它能做什么？ | 按需召回最相关的子图；压缩旧对话；标识事实、假设、冲突和被取代结论。 |
| 它不能做什么？ | 不替代项目文件；不允许用删历史掩盖仍有关的冲突；不能把无证据“已通过”伪装成事实。 |

### 文件状态和 Memory Graph 的区别

```text
文件状态：当前仓库里有什么
Memory Graph：为什么这么改、用户到底要求什么、什么已证实、什么仍未知
```

例如，`src/config.ts` 中出现 `parseConfig` 是文件事实；“用户要求此公开 API 必须名为 `parseConfig`，并且验证命令以退出码 0 通过”是任务记忆。

### 记忆节点如何避免自我欺骗

节点有两组标签：

```text
kind（内容性质）：
directive   约束或要求
fact        有证据支持的事实
hypothesis  待验证的推测

status（当前有效性）：
accepted    目前成立
disputed    有冲突或证据不足
superseded  已被后续证据取代
outdated    已不再适用
```

例如：

```text
hypothesis / disputed：
“全量回归可能通过；证据缺口：未执行完整命令。”

fact / accepted：
“`go test ./...` 退出码为 0，见任务日志。”
```

这比把两者都写成“测试通过了”更安全。

### 为什么要有 subgraph organizer 和 `memory_apply`

Memory Graph 可以很大，但每个任务不应携带全部历史。**subgraph organizer** 是专门整理记忆的 Agent。

它优先保留：

```text
原始用户/Task Info 契约
    ↓
当前硬约束与验收标准
    ↓
有证据的事实、未决缺陷
    ↓
其他实现细节
```

它的意义是防止“最新修复问题”挤掉最初需求。例如最新任务在修一个错误信息，下一轮却忘了用户原本还要求公开 API 签名。

`memory_apply` 则是面向整理者的原子批量修改工具：一批 create / update / status / delete / attach / detach 要么全成功，要么全不改变。用户原始要求、Task Info 等“契约层”受工具强制保护，不能被整理者删除或改写。

审计文档特别指出旧问题：没有证据的“API 和测试已通过”被作为 accepted 记忆选入后续任务，形成假阳性自我强化。新机制通过证据锚、`disputed` 状态和取代关系来阻止这一点。

## 5. Tool Layer、Persistent State、Logs / Monitoring

### Tool Layer：统一的工具入口

Tool Layer 不是“一个会做事的 Agent”，而是角色调用文件、命令、记忆、协调等能力的受控入口。

| 问题 | Tool Layer 的答案 |
|---|---|
| 它是干什么的？ | 校验工具参数、绑定环境、路由调用、统一结果与错误、发布事件。 |
| 为什么需要它？ | 否则每个角色可能绕过权限、使用不同错误语义，日志也无法关联。 |
| 它能做什么？ | 让工具调用可验证、可记录、可取消、可正确绑定到相应工作区。 |
| 它不能做什么？ | 不应把角色策略、任务调度或绕过 Memory/VFS/Sandbox 的路径塞进去。 |

### Persistent State：让运行时能恢复，但不替人做决定

Persistent State 保存 Coordination Graph、Memory Graph、VFS 等组件的状态，以便保存、加载、恢复和清理。

它不能“自动重放模型或工具副作用”。例如，不能因为进程恢复就再次执行一个可能有副作用的命令；恢复必须安全、可审计。

### Logs / Monitoring：只观察，不操控

Logs / Monitoring 记录事件、延迟、错误率、队列长度、任务状态、资源使用等。

它像飞行记录仪，而不是自动驾驶仪：

```text
任务与工具事件
       ↓
日志 / 指标 / 告警
       ↓
人和评估系统观察

不能反向改写任务控制流
```

治理文档要求监控不能保存提示词、模型增量、秘密值或任意文件内容。它只能提供观察证据，不可反向操控业务流程。

## 6. 为什么 Verifier 比“测试通过”更严格

新提示词草案把 Verifier 的目标描述为：验证用户真正想要的结果，而不是验证 Executor 是否照计划做了事。

例如，用户要求：

> `parseConfig` 对合法输入成功，对非法输入返回指定错误。

只跑一个合法样例并不能证明要求成立。Verifier 要先构造目标命题，再建立能支撑它的验收条件：

```text
目标 G：
parseConfig 在约定输入范围内符合接口、成功与失败语义

条件：
C1：公开入口与签名正确
C2：合法输入行为正确
C3：非法输入行为正确
C4：指定错误/输出语义正确
C5：构建通过
C6：新增验收测试通过
C7：全量既有回归通过
```

它还要反问：

> “这些条件都满足时，功能仍然可能没实现吗？”

如果答案是“可能，例如测试只特判了一个输入”，条件还不够。这个“必要性与充分性”检查的目的是防止把局部绿灯错当最终验收。

审计里最严重的问题之一，就是内部 Verifier 在网络或依赖受阻时，把静态阅读或自写测试当作通过依据。更新后要求：

```text
最终 PASS 必须有：
构建/编译命令 + 退出码
新增验收命令 + 退出码
全量既有回归 + 退出码
独立公共入口 probe
逐项 Task Info 映射
```

如果关键验证真的无法执行，应先尝试本地缓存、vendored 依赖、无需外部服务的测试子集或其他 runner；仍无法证明时是 INCONCLUSIVE，不是 PASS。

## 7. 四篇文档之间的关系与设计演进

| 文档 | 它解决的问题 | 在整体中的位置 |
|---|---|---|
| [agent-prompts-before](agent-prompts-before.md) | 记录修改前的提示词基线。 | “原来系统如何要求各角色工作”。 |
| [prompt-update-deepswe-audit](prompt-update-deepswe-audit.md) | 用 DeepSWE 评测归因失败，提出并记录一轮修复。 | “为什么旧规则失败，以及怎样用提示词与少量代码改动修复”。 |
| [agent-prompts-after](agent-prompts-after.md) | 给出更进一步的提示词修改稿，重点是 Planner 驱动的任务内动态并行与更紧凑的职责边界。 | “下一版角色协作设计”。该文自称修改稿、尚未写回运行时配置。 |
| [architecture-governance](architecture-governance.md) | 定义模块边界、允许改什么、评估什么，以及哪些依赖关系不能随意改变。 | “宪法 / 架构护栏”。 |

为什么会有 before / audit / after？

```text
before：原来的规则
   ↓
audit：用真实评测失败定位规则缺口
   ↓
after：针对更深一层协作与并行问题提出的新设计
```

审计不是泛泛地说“效果不好”，而是把失败映射到具体机制：

- 内部 PASS、官方失败：缺少“官方等价门禁”和证据要求。
- 大量 INCONCLUSIVE：没有要求先寻找替代验证路径。
- 287 个 root、0 个 helper：只有“不要乱拆”的限制，没有正向的并行拆分方法。
- 原始契约被最新缺陷挤掉：记忆没有足够的证据、优先级和取代机制。
- 工作区有改动但没有可评分交付：Executor 未明确检查最终正常工作树。

`architecture-governance` 的地位最高。它不规定某一轮 prompt 的具体措辞，而是规定角色、图、VFS、Sandbox、Memory、持久化与观测之间允许的边界。比如“Manager 不直接操作项目文件”“Verifier 不修复”“监控只能单向观察”都来自这里。任何新箭头、新角色、新图边语义，按文档都需要显式人工批准。

## 一句话总结与源码阅读顺序

**Threadmill 是一个把“理解需求、规划、实现、独立验收”拆成受控角色，并用任务图、隔离工作区、证据记忆和运行时治理把它们可靠连接起来的 Agent Runtime。**

如果接下来读源码，推荐顺序是：

```text
architecture-governance.md
→ coordination（图、任务、join/help）
→ agent（manager / planner / executor / verifier 的装配和上下文）
→ VFS
→ tool layer
→ memory graph 与 compact / organizer
→ sandbox
→ persistent state
→ logs / monitoring
```
