## 要教会的方法及实际表现

| 角色／遇到的情形 | 希望看到的行为 | 本轮判定 |
| --- | --- | --- |
| Manager 首次接完整任务 | 找到多个真实独立工作面，首轮直接建图 | 部分支持：应用出现 backend/frontend/integration；早期版本仍把整题交单 task |
| Manager 追加工作 | 从真实快照保留已有 task、Info、全部边，再追加消费关系 | 一次追加恢复验证通过；最新V4更改已启动Info、抄错既有输入边，连续三次被拒，尚未学会可靠处理中途追加约束 |
| Manager 处理等待 | 把独立 C 提前做，只有消费 B 的 D 等待 | 未通过完整验证：多个集成 Planner 整体等待上游，没有充分前移独立工作 |
| Manager 阶段发布 | 发布可用成果，后续快照保留仍需要的已交付文件 | v14 会话试验有支持：两次不覆盖兄弟成果、一次及时发布累计后端、V4 最终交齐前后端；不是新系统提示独立 A/B |
| Manager 确认修改结果 | 以工具成功返回和真实图说明是否生效 | 未达标：V4三次修改被拒后仍称已纳入，评测者核对反馈后才更正；原图保护正常 |
| Planner 展开实现 | 用共享契约分配独立所有权、并行门禁和合入责任 | API 四 helper 有真实行为证据；跨层响应字段约定仍有遗漏风险 |
| Planner 同型分片／Executor 补新边界 | 依据新证据展开此前未物化的独立输入 | 未触发；已撤回本轮候选，不能把计划内 Help 当作验证 |
| Executor 环境与交付 | 依赖/缓存放临时执行环境，交付保留锁定和重建入口 | ML 支持临时化；V7 最终验收新生成 .venv 并发布2890条缓存路径，说明 v8 清理描述未普遍生效；v15 在 V4 新消费任务中清空缓存、65文件不变且重新安装启动成功；V7 最终发布37文件无缓存，原33文件无缺失；但两个helper内部交接先带入193项字节码差异，未解决所有内部交接成本 |
| Executor 等待与合入 | Help 后释放，实际消费固定出口，检查组合结果 | 有计划内 Help 和固定出口合入；尚无大规模独立工作覆盖证据 |
| Verifier 审查应用 | 从真实公共入口验证关键用户动作，分清局部/集成范围 | API 验证有效；以 bundle 文本代替实际浏览器的证据不足，由评测者补验 |
| Verifier 审查研究 | 核对来源、假设、推导条件，尝试反例 | 未达标：脚本能运行与引用存在未阻止错误的上下界推断 |
| Organizer 整理记忆 | 有界读取、保留来源、复用成果，只查影响决定的内容 | V7 两个集成 helper 后记忆整理 8m51s、23 次模型调用、722402 tokens；V4 两修订合入为 7m6.7s、13 次、451191 tokens。含上游等待，不是图计算 CPU 时间。另一次2份证据合入：文件差异195项（193为字节码缓存），5m12s/35调用/885059 tokens；随后记忆6m47s/13调用/469729 tokens、3次误写共同只读节点被拒。未证明高效记忆图 |
| 长期驻留任务 | 默认无合出边；激活完 idle；真实消费者接所需固定出口 | 用户方法已写入角色提示；本轮三个场景没有充分触发，不声称运行验证通过 |

并发指标必须区分：逻辑 task 活跃、模型调用活跃（包含上游等待/重试）、命令执行槽占用。15 秒采样的单项目显式模型活跃峰值为 5；截至此记录各项目同一采样点合计峰值为 9。早期不兼容的 99 条行未用于该统计，输入整理事件在旧构建还存在漏计。没有几十／上百有效并发证据，更没有千 Agent 规模证明。

扩图不足的已观察原因包括：整题先交单 task、真实消费者之前的角色被整体阻塞、Manager 的图修复错误占住协调回合、共享契约欠完整。上游限流和容量错误另计，不能把这些方法问题都归因于服务，也不能靠制造许多无价值 task 达标。

## 已修复和仍存在的故障

| 范围 | 已完成修复／证据 | 保留的边界 |
| --- | --- | --- |
| 大请求恢复 | Manager待恢复正文约103万字符，重复重开仍400；本轮运行窗口1M→256k触发压缩，随后请求成功、原任务启动 | 不证明400根因或Grok真实窗口；成功输入仍332252 tokens，软预算不是硬上限；压缩仍有成本 |
| 上游容错 | 可配置重试；Retry-After；实际限流/无通道/过载分类；可撤回的 Web 流重试 | 运行有 60 次预算、可取消等待；不将永久错误无限重试，不保证外部服务成功 |
| 活动观测 | 输入文件/记忆整理补 Events；隐藏压缩流与重试实时显示；计数去重 | 老构建遗漏的用量和活动无法从新指标补回 |
| Web 状态 | Help 显示 waiting；恢复中的失败 task 按真实活动显示；错误项目不被失效队列永远标忙 | busy/快照来自多次读取，不声称原子；恢复不等于原任务验收通过 |
| Web 体验 | 图拖拽缩放、侧栏、项目切换、报告折叠、移动布局已实操；同次busy切换计时倒退与无Manager活动却显示Thinking已修复复验 | 尚未做千节点渲染；跨 task 依赖边数据已接入但完整边布局未实现 |
| 会话恢复 | 新网关可打开已有项目状态并继续工作 | 项目列表/聊天/事件缓存仍是进程内；跨进程互斥与历史回放未实现；Working 时钟重载可能重置 |
| 应用交付入口 | V4 默认 Node24 从旧 ABI 缓存自行 rebuild 成功，再从无缓存交付安装启动成功；V7 原目录残缺venv由./start.sh自行恢复，实际目标prefix及GUI原数据通过 | Agent隔离副本与评测者用户目录证据分别记录；启动回归未无故重跑完整业务矩阵 |
| 网关退出 | 05:33 的8795有kernel OOM证据、exit137、anon RSS约11.5GiB；原active状态经GUI重新打开后恢复 | 诊断构建GOMEMLIMIT=4GiB仅是软目标；02:40三个旧网关exit0仍属另一未知事件 |
| 建图后启动 | 新任务已建图且enabled，Manager回执stream_incomplete重试期间未启动；runReady通常由AfterTurn触发 | 回合结束、打开无pending项目、其他task结束均有触发点；未改变提交/冻结或调度时机 |
| VFS 快照资源 | 独立复现：4MiB祖先文件、64个纯逻辑子环境，GC后堆增约260MiB；pprof指向cloneBlob | overlay_bytes仍仅4MiB，漏计祖先快照；未修核心存储，不宣称旧OOM已完整归因或大集群内存达标 |

页面观察记录没有应用 JavaScript exception；404 favicon、预期的 401/409、浏览器原生密码弹窗和操作脚本选择器错误单独分类，不用于伪造“页面崩溃”。

最后截图还显示Manager正文中的Markdown强调、行内代码标记按纯文本显示。这是仍在的排版限制；不影响内容完整性，但不能把本轮GUI复验称为全部体验问题已解决。

后续用户明确要求Markdown渲染后，此项已修复：真实Grok示例的标题、强调、列表、引用、表格、代码和链接在桌面/390px窄屏显示正常；10项离线浏览器检查覆盖安全清理、代码保真、缓存更新及逐字符流式前缀，全部通过。其余依赖图/历史回放限制仍有效。
