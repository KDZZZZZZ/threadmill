# Agent 方法评估：2026-09-12 GUI 迭代

并发统计截至 13:31 +08；后续观察更新到 15:32。两份 CSV 应用与六文件恢复已交付，三个格式项目停在上游错误。本文区分人类要求、已观察的行为与尚未覆盖的能力，不把任务数量当成最终交付或有效并行度。

## 人类明确要求

- 保留详细、可泛化的拆分方法，直接写进不同角色的提示词，不改成 skill，也不缩成一句要求一百并发。
- Planner、Executor、Verifier 都能自主请求 Help；帮助属于实际请求者，结果返回其 Resume。
- A 需要 B 时识别不依赖 B 的 C 和依赖 B 的 D，让独立工作先推进，在实际消费点合流。
- 等待时暂停，不保持模型活跃；长期任务默认不合入其它任务，消费者只接所需固定出口。
- 真实任务经 GUI 提交和观察；每次提示词调整先记录预测，按具体行为验证，不保留含糊的收益主张。
- 五个角色的平均静态提示词与工具说明控制在 10k token 以内。

## 逐角色看方法

| 角色 | 当前保留的方法 | 已有行为证据 | 剩余问题或未覆盖项 |
|---|---|---|---|
| Manager | 从承诺列能力，按所需知识和决定划 owner，检查输入、写入面、验收与真实依赖；已知可开工工作批量建图，后续随证据展开 | v19 首次分出八组格式能力、CLI、README 和集成；包骨架结束后各分支同时开始 | 两份 docstring 包标记被单列为九个 Planner 的共同前置，耗时 3m57s；小日志任务也单列了只复核已有四行输入的任务。须校准任务粒度和前置的价值 |
| Planner | 本层先完成必要语义和最小共享契约，再委派可独立验收的实现；契约未定不等于所有消费者永久不可拆 | v18 CLI 因记录结构未定而 `split:none`；v19 CLI 先定义记录、统计和函数接口，再把处理引擎、HTML 分开，自己保留入口与集成 | 同一 v19 计划仍把可提前做的 CLI 入口准备留到 Help 返回以后；不能仅凭出现 Help 判编排正确 |
| Executor | 使用已确认的 owner/契约；按当前输入提交 ready 工作，合流或新证据出现后复查剩余能力；局部叶子直接实现 | v19 的八个格式组和 CLI 共提出九次 Help，按实际 Executor 身份接回 | 这些主要执行 Planner 已列出的工作；独立发现计划外新工作尚未覆盖，不能把未触发误判为自主权无效 |
| Verifier | 按用户目的和公共入口独立取证，保留裁决；可自行请求独立证据；通过不等于只看单测数量 | 较早 v16 的 Web UI 验收发现默认参考表行阻碍可选上传，并触发修复后通过 | v19 Verifier 自主请求 Help 尚未覆盖；最终产品的组合验收仍在运行 |
| Organizer | 按问题、适用条件、task/activation 和证据来源组织记忆；复用共同部分，只处理相关差异，保留历史范围 | 合流记录显示文件处理之后进入独立 input-organizer；当前历史与固定文件来源仍被保留 | 多轮 neighbors/sources 查询和较长模型回合构成实际成本；尚未证明每次查询是否必要，不能把这段耗时归给文件系统 |

v19 的共享契约修订符合一次真实任务的行为预测；版本之间并非严格因果 A/B。用户要求的三角色自主权是应满足的语义，不以某个触发条件是否在一次运行中出现来决定存废。

## 评估拆分是否有效

1. 每项用户承诺是否有负责交付的 owner，当前图结束后是否仍有能力尚未展开？
2. 每个委派单元是否具有可用输入、清晰消费方式、独立验收与足够的工作量？
3. 共享前置究竟缺少哪项决定或产物？哪些准备、实现、取证可以先做？
4. requestHelp 暂停调用者之前，独立前缀是否已完成或放进同一批任务？
5. 合流后是否只处理剩余工作，避免重做已完成实现、反复复核同一证据？
6. 最终组合是否通过真实入口验证并完整发布，而非只得到很多局部 PASS？
7. 减少的关键路径时间是否足以抵消额外角色、编排、记忆整理和合流开销？

这些检查逐处判定，不以一次未达到固定并发数为由删除整套拆分方法。

单文件恢复的反例也暴露了成本：29m17s 的失败激活中，输入 Organizer 21 次模型请求用时约 10m03s，Executor 发起的记忆查询又用时 5m40s，Verifier 尾部压缩 1m42s；三个不重叠记忆阶段合计占墙钟约 59.5%。这不是磁盘复制耗时。输入 Organizer 各次请求累计输入约 117 万 token，是含重复上下文的处理量，不是唯一上下文或未缓存账单。评估有效拆分需要同时记录这种合流开销，不能只扩展节点数。证据 `receipt-restore-phase-events.json`、`receipt-restore-cost-breakdown.json`。

## 已测量的边界

静态完整请求包含工具 schema 和包装，排除动态任务、协调图和记忆。o200k 估算平均 4,959.2 token；cl100k 平均 6,199，最大 7,768。它们不是 Grok 精确 tokenizer。

从完整 model start/end 日志按角色归类：

| 冻结版本 | model 事件峰值 | 任务三角色峰值 | Executor 峰值 |
|---|---:|---:|---:|
| v16 | 6 | 5 | 3 |
| v17 | 11 | 10 | 7 |
| v18 | 12 | 11 | 9 |
| v19 | 11 | 10 | 6 |

每列是各自峰值，不可相加。model 事件包括 Manager、输入 Organizer 等；独立 memory 事件未混入。已建任务和等待 Help 的任务不算正在调用模型。尚无几十、上百或上千任务 agent 有效并发的证据。

控制面还有两个已定位的限制：Help 正文逐条进入 Manager 的 FIFO 回合，当前图不提供其余待处理请求正文；全图和报告进入上下文后还会随历史重复。v17 一次 Manager 请求由上游回报输入 429,133 token，不能将其归为静态提示词长度。

## 系统修复与提示词效果分开

- GUI 切换项目时恢复 Help Waiting：旧版浏览器回归 6 项失败，修复后 7/7 通过，真实项目也恢复等待项。未改变调度。
- 编排回执去重：新候选 GUI 任务创建集成时，回执保留 12 个输出引用，重复报告正文为零；原图和紧随其后的模型状态块仍保留对应 27,212 字符报告，文件/记忆引用一致。coordination/manager race 与全仓测试通过。该收益限于回执展示，尚非全图渐进披露或端到端耗时结论。
- Btrfs 当前是 ext4 上的镜像，真实任务 reflink 未回退；不能报告为原生磁盘对照。输入记忆整理的模型耗时须另计。
- 临时文件输入和输入 Organizer 循环遗漏 YAML 工具说明：已修复加载，Provider 请求边界四个回归分支由失败变通过，race 与全仓测试通过；未改变隔离集合或输入事务语义。14:21 部署至 8789 后，恢复任务的 11 次 input 调用无参数错误，但其文件采纳决策错误，最终 Verifier FAIL；不把协议调用成功当成语义合流成功。上述五角色静态预算不证明这些临时阶段原先已收到完整说明。
- 新用户消息到达时，Thinking/Working 错挂上一条完成答案：修改前浏览器回归 4 FAIL / 2 PASS，修复后 6/6，通过真实 GUI 后续消息验证。只修改展示位置。
- 只看差异子图分配自动 ID，会撞到隐藏共同节点：合法 create 在旧代码复现 `mem-1 is read-only`。修复保留所有共同身份占用，同时不扩大可见范围，支持批量创建及显式 ID/状态保留；race 与全仓测试通过，已随最终构建部署至空闲后的 8789 候选。不能把这类报错一概当成 agent 不听只读规则，尚无部署后真实合流耗时对照。
- 包装为 `upstream_error` 的“stream disconnected before completion … unexpected EOF”未进入重试，v17 Manager 于 15:05:34 直接报错。补充已观测形状分类后，HTTP/SSE 正例从一次失败变为重试成功，非断流 EOF 和其他永久错误仍不重试；provider/CLI race 与全仓测试通过，已部署至 8789 候选。v17 所在的 8788 未重启，不宣称它已经恢复。
- 根目录条目依赖被命令缓存漏记，新增文件后 `ls` 可能重放旧列表，造成“可读但列不出”的假象和额外恢复动作。跨 agent 的公开 Scheduler 回归先红后绿；根目录映射为 `.`，沿用现有目录摘要，未变目录仍命中；旧缓存命名空间隔离。此修复不等于所有 stat 元数据依赖都已精确建模，亦不能推翻第一轮真正 discard 当前文件的独立错误。
