## TUI 缺陷

1. 普通 task 名称被 `task-` 前缀过滤，正文有运行事件却显示 `tasks 0` 和 `0 NODES`。前一版补丁只移除了前缀判断。
2. 新节点是 `taskID:activation:role`，旧解析器只切第一个冒号，导致角色被丢弃；状态查询还在找 `task:role`，所以三角色一直显示 wait。取消前缀过滤不足以修复。
3. 放宽前缀后的实现会把独立 organizer 当普通 task，产生假节点和计数。
4. persistent task 的下一次激活没有清除上一激活的角色状态，迟到旧事件还可能覆盖新状态。
5. GRAPH 当前只画固定三角色链，未展示真实跨 task 依赖；恢复后只靠后续事件重建图，也不能展示完整历史。此项需要接协调图只读快照，属于后续 UI 接口接线缺口，不能声称本轮已修复。

前三类角色状态问题与 persistent 重置在 `internal/tui/` 做显示层修复；不改调度语义。回归接缝为 RuntimeEvent → Update/View，覆盖新 ID、checkpoint、organizer、第二次激活及迟到旧事件。

验证已完成：新增三组回归先失败后通过；`go test ./internal/tui ./internal/cli ./internal/provider ./internal/manager ./internal/coordination` 与 `git diff --check` 通过。真实 Kitty TUI 事件回放显示 9 个角色节点、2 个未结束 task：已完成的 upstream_pin 三角色为 ✓，baseline_run 的 executor 活跃，service 第二激活只有 planner 活跃，input-organizer 没有变成第四个 task。截图与事件驱动程序位于审计目录 `tui-replay.png`、`tui-replay.txt`、`tui-replay-main.go`。该回放不含远端模型请求，不计入真实测评并发。

## 提示词表现

**已观察到的能力**：Manager 能一次创建多个普通 task；已知独立任务可并行；help 能展开多个证据方向；非法边端点在运行时被拒绝后可以恢复；产物有固定出口和发布记录。普通 task 并发的改善是行为观察，尚无严格随机对照，不能完全归因于某一句话。

**明显不足**：没有达到几十/上百模型并发；初始粗粒度 owner 之后不易继续展开；Verifier 反复取证消耗大量输入上下文，且核验数量与已发布报告仍有错位。应用 `core-app` verifier 有 55 次模型调用，另两个 verifier 各有 51 次；这些是调用次数，不等同于全部无效重复，但需要按新增证据审计收益。

| 角色 | 本次表现 | 下一步教会的方法 |
| --- | --- | --- |
| Manager | 可以提交多个 task，但 App 首层 core→admin→E2E 仍是消费串行；多次改不可变输入 | 按真实消费点接边、补新 task 而非改已开始输入、先审计报告再认为验收通过 |
| Planner | Research 仍由主 planner 经 help 展开四个方向；App planner 148 次模型交互、102 次 bash | 先冻结共享契约，按独立范围批量分片；确定 owner 后把局部答案交给它 |
| Executor | 有真实实现产物；但 App 675 次模型交互，部分 helper 缺输入仍消耗多轮 | 输入不具备就明确缺口；新证据出现时补充有界 frontier，不把所有未知留本层 |
| Verifier | 有原始门禁证据，也发现了引用反证；最终验收与修正发布没有闭合 | 逐契约裁决、区分通过/阻塞/未验证；以新反证决定重开范围，不把局部修正当全局已交付 |
| Organizer | 有整理调用，但没有单独测得召回精度与上下文节省收益 | 保存可复用结论与来源，按决定级缺口返回小视图；目前不能声称已证明记忆图高效 |

| 现有规则冲突或缺口 | 为什么会压低有效并发 | 下一次单独验证的替换方向 |
| --- | --- | --- |
| Manager 要首轮拆分，同时 Task Info 规则禁止“臆造内部模块或拆分” | 容易把必要责任细化误判为新增用户范围 | 保真用户要求，允许在授权目标内推导可独立验收的责任边界；禁止新增产品目标和硬约束 |
| Executor 无 frontier 不临时造 helper | Planner 漏拆后，即使出现新证据也只能由一个 Executor 继续做 | 新证据显露独立责任边界时只补受影响 frontier，保留既有 owner 与契约 |
| “一个规则覆盖一类，不枚举同型成员” | 统一契约容易被误当成一个执行 owner | 复用一份契约，按真实独立对象/输入分片形成宽 frontier |
| 对输入 probe 的限制覆盖所有输入核对 | 共享环境可行性、兼容性等正交证据面被留给单个消费者 | 轻量输入核对留本层；可改变共享契约且独立可验收的证据面可委派 |
| Verifier 缺少基于新增证据的收敛规则 | 已确认范围反复进入上下文，长尾占住交付链 | 同一证据面确认后只因新反证或状态变化重开，必要验收不省略 |

这些是待验证替换建议，本报告不把它们直接叠加进正式提示词。每轮先记录预测，再只改一组、同题复跑；不符合预测则撤回或修订。

最后新增的“edge 端点必须为完整 node ID”文案没有完成 TUI 对照，已撤回到 v5 文案。checkpoint ID 也不能被误约束成只有三段的格式；候选改写必须保留工具实际返回的 checkpoint。

## 达到几十到上百并发的验收方法

固定模型与资源配置，在有真实宽工作面的任务上逐级测 32、64、128 个独立工作单元；单个 digits baseline 不足以验证百级并发。适用任务可为批量独立数据分片分析、多个可隔离模块的兼容性迁移、跨大量来源的独立证据核验；最后保留独立的汇总与交叉验收责任。

| 观察项 | 验收方式 |
| --- | --- |
| 发现独立工作 | 首轮/后续 frontier 覆盖可独立验收对象，不能靠无交付价值的 probe 凑数量 |
| 实际并发 | 同时记录模型 start/end、task running、命令 active/queued；分别报告峰值与持续时间 |
| C/B/D 拆分 | B 与 C 同时推进，D 只等真实 B 出口，集成边接实际消费点 |
| Manager 扩图开销 | 记录 help 提交 → 编排完成 → 首个模型请求的延迟；批量提交已知 ready 单元 |
| 共享前置 | 契约/fixture/公共来源准备一次后展开；不为每个 worker 重做同一调查 |
| 等待释放 | 依赖未齐不调用模型、不轮询保活；持久 idle 不阻塞交付 |
| 记忆收益 | 每新增有效证据的输入 token、整理调用、订阅节点数；不只看图大小 |
| 完成质量 | 每个硬契约映射原始证据；内部修正、固定出口与用户可见报告必须一致 |
| 扩展收益 | 增加并发后吞吐/端到端时间改善，重复工作率和集成成本不抵消收益 |

代码层没有发现 `tasks`/`units` 的数量截断；命令槽位 64、heavy 默认 8 不等于模型并发上限。Manager 的报告/help 进入同一 FIFO，且回合结束才启动 ready task，可能成为大规模扩图瓶颈；当前只有代码依据，尚未测得它是本轮主瓶颈，不在提示词任务中改核心调度。
